# Task: Account-Übernahme per Vorab-Registrierung schließen (H5)

Kontext: Cloudflare-Worker-Projekt (TypeScript, keine npm-Runtime-Dependencies, deutscher Code).
Lies zuerst AGENTS.md und README.md (Abschnitt "Wichtige Design-Entscheidungen").
Der Code ist deutsch kommentiert und benannt - so bleiben. Style: 2 Spaces, double quotes,
semicolons, benannte Exporte. KEINE neuen npm-Pakete. Nicht committen.

## Sicherheitsproblem (H5)

Die Registrierung (src/auth.ts handleRegister) prüft die E-Mail-Adresse nicht.
Ein Angreifer registriert die Adresse des Opfers mit eigenem Passwort. Meldet
sich das Opfer später per Magic Link an (src/magic-link.ts findOrCreateUser),
landet es in genau diesem Konto - der Angreifer kommt per Passwort weiter
hinein und liest alle Listen mit.

## Gewünschte Lösung

### 1. Migration 0012 (migrations/0012_email_verified.sql)

```sql
ALTER TABLE users ADD COLUMN email_verified_at INTEGER;
```

Kommentar im Kopf der Datei (deutsch, Stil der anderen Migrationen): Zweck -
NULL = nie per Magic Link bestätigt; der erste Magic-Verify eines
passwortgeschützten Kontos bestätigt die Adresse und entzieht gleichzeitig
einem etwaigen Angreifer-Passwort die Grundlage (siehe auth.ts handleLogin).

### 2. Magic-Verify: E-Mail bestätigen + Angreifer-Passwort verwerfen (src/magic-link.ts)

In handleMagicVerify nach erfolgreichem findOrCreateUser:

- Das 用户-Handling bleibt in findOrCreateUser; ERGÄNZE dort bzw. direkt danach
  eine Logik `verifyUserEmail(env, userId)` (Helper in magic-link.ts):
  - `UPDATE users SET email_verified_at = ?, password_hash = 'magic' WHERE id = ? AND password_hash NOT LIKE 'pbkdf2:%'`
    ist NICHT genug. Korrekte Semantik:
    1. Zeile lesen: `SELECT email_verified_at, password_hash FROM users WHERE id = ?`.
    2. Ist `email_verified_at` NULL und `password_hash` beginnt mit `pbkdf2:`
       (Konto also per Passwort registriert und nie verifiziert):
       `UPDATE users SET email_verified_at = ?, password_hash = 'magic' WHERE id = ?`
       UND alle Sessions des Users löschen
       (`DELETE FROM sessions WHERE user_id = ?`), damit der Angreifer sofort
       rausfliegt. Kommentar: Verifizierung über den E-Mail-Beweis entzieht das
       nie bestätigte Passwort (H5).
    3. Sonst (bereits verifiziert oder Magic-Sentinel): nur
       `email_verified_at` setzen, falls noch NULL:
       `UPDATE users SET email_verified_at = ? WHERE id = ? AND email_verified_at IS NULL`.
  - MAGIC_SENTINEL-Konstante weiter nutzen ("magic").
- Reihenfolge: verifyUserEmail VOR createSession ausführen, damit der
  Session-Wipe des Angreifers nicht die frische Session des Verifizierers
  erwischt.

### 3. Passwort-Login unverändert, Registrierung unverändert (src/auth.ts)

Kein Verhalten an handleRegister/handleLogin ändern (die Limits aus Task 1
bleiben). Nur falls sinnvoll: ein kurzer Kommentar bei handleRegister, warum
kein Verifizierungszwang eingeführt wird (Passwort-Konten ohne Verifizierung
zulässig; über Magic Link kann die Adresse jederzeit nachträglich übernommen
werden - gewollt, denn der E-Mail-Inhaber beweist damit Besitz).

### 4. Realtime-Test erweitern (scripts/realtime-test.mjs)

Der Magic-Link-Versand braucht RESEND_API_KEY und ist im lokalen dev leer -
daher kann der Verify-Pfad im Realtime-Test nicht end-to-end getestet werden.
Stattdessen Unit-Test:

- Neue reine Funktion in einem testbaren Modul: ziehe die Entscheidung "verifiziert
  mit Passwort-Verwerfen?" als reine Funktion heraus, z. B. in src/magic-link.ts:

```ts
export function emailVerifyAktion(emailVerifiedAt: number | null, passwordHash: string): {
  setVerified: boolean;
  discardPassword: boolean;
  wipeSessions: boolean;
}
```

  - (null, "pbkdf2:...")  -> { setVerified: true, discardPassword: true, wipeSessions: true }
  - (null, "magic")       -> { setVerified: true, discardPassword: false, wipeSessions: false }
  - (123,  "pbkdf2:...")  -> { setVerified: false, discardPassword: false, wipeSessions: false }
  - (123,  "magic")       -> { setVerified: false, discardPassword: false, wipeSessions: false }
- src/magic-link.test.ts NEU: diese 4 Fälle plus Randfall (null, "garbage") ->
  gleiche Behandlung wie "magic" (setVerified, kein Verwerfen).
- handleMagicVerify nutzt emailVerifyAktion und führt die daraus folgenden
  Updates aus (einzelne UPDATE-Statements, wie oben beschrieben).

### 5. README.md

Im Magic-Link-Abschnitt einen Satz ergänzen: "Der erste Magic-Link-Login
bestätigt die E-Mail-Adresse; bei einem bisher unverifizierten Passwort-Konto
wird dessen Passwort verworfen und alle Sessions gelöscht - so kann sich niemand
vorab mit einer fremden Adresse registrieren und später mitlesen (Account-
Übernahme-Schutz)."
